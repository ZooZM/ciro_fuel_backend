# Data Model: Web Dashboard Authentication & Taqnyat SMS Provider

**Feature**: `015-dashboard-auth-taqnyat-sms` | **Date**: 2026-09-03

Two new persisted shapes, one new embedded sub-document, one new JWT claim, four Redis key families,
and three enum additions. Nothing existing is renamed or removed.

---

## 1. `User` — changed (existing collection)

### 1.1 New embedded sub-document: `activeSessions`

```
activeSessions: ActiveSession[]      // default []
```

```
ActiveSession {
  sid:       string     // required, immutable — 32 bytes of randomness, hex
  createdAt: Date       // required, immutable — the eviction ordering key (research R1)
}
```

- `_id: false`. Unlike spec 011's `StopEvent`, nothing addresses one of these by id — `sid` is the
  identifier, and it is generated by the platform at sign-in.
- **Written only for SUPER_ADMIN, FUEL_COMPANY_ADMIN and TRANSPORT_COMPANY_ADMIN.** For DRIVER and
  CLIENT the array is never populated, and `validateActiveSessionWithScoping` never consults it
  (research R1 — this is what makes FR-033 structural rather than a test result).
- Bounded by `auth.maxAdminSessions` (default 3). The bound is enforced in `openSession`, not by the
  schema; a schema-level cap could not express "evict the oldest".
- No `lastSeenAt`. Recording one would mean a write to `User` on every authenticated request
  (research R1). Eviction is by `createdAt`, which FR-038 ("the oldest session") is satisfied by.

### 1.2 `sessionGeneration` — meaning narrowed, field unchanged

Keeps its type, its default and its comparison in `validateActiveSessionWithScoping`. What changes is
**who bumps it**:

| Event | Before | After |
|---|---|---|
| DRIVER/CLIENT login | bump | bump (unchanged) |
| DRIVER/CLIENT logout | bump | bump (unchanged) |
| Admin login | bump | **no bump** — `openSession` instead |
| Admin logout | bump | **no bump** — `closeSession` instead |
| Password reset (any role) | bump | bump **and clear `activeSessions`** |
| Deactivation (any role) | bump | bump **and clear `activeSessions`** |

Clearing the array alongside the bump on the two revoke-all paths is what makes "every session ends"
true for administrators. The bump alone would already refuse their tokens (the `sgen` comparison
runs for every role), so the clear is belt-and-braces — but leaving stale entries behind would let
the array drift up against the cap and silently evict a legitimate new session.

### 1.3 `phone` — constraint tightened (research R5)

Value and type unchanged. Two changes around it:

- **Index**: the existing partial unique index is extended from `{ role: { $in: [CLIENT, DRIVER] } }`
  to include the three administrator roles. **Requires the placeholder normalisation below to run
  first** — index creation fails outright while two documents share `'N/A'`, and on this platform a
  failed index build means the service does not start.
- **Validation**: creating or updating an account with an administrator role requires a phone
  matching the platform's existing `E164_PATTERN` (already used by `LoginDto`). `'N/A'` stops being
  an acceptable administrator phone.

**Migration** (pre-production, so a normalisation rather than a dual-write):

1. Every existing administrator whose `phone` is not E.164 is assigned a real number, or the account
   is deactivated. There is one such account in a default install — the seeded SUPER_ADMIN.
2. `scripts/seed-super-admin.ts` stops writing `phone: 'N/A'` and requires
   `SUPER_ADMIN_PHONE` in E.164 form.
3. Only then is the index extended.

An administrator left with a non-E.164 phone after step 1 is not broken — they simply cannot use
code sign-in, and fall through to email-and-password (FR-064). This is the documented outcome for
"an administrator has no mobile number on file".

## 2. `LoginCode` — new collection

Modelled on `PasswordReset`, and **deliberately a separate collection from it** (research R10): both
apply a supersede-on-reissue rule, and sharing one collection would make a sign-in request silently
invalidate a password-reset code in flight.

```
LoginCode {
  userId:     ObjectId  → User   // required, immutable
  phone:      string             // required — the number the code was SENT to, captured at issue
                                 //   so a phone change mid-flight cannot redirect a live code
  hash:       string             // required — salted SHA-256 of the code (OtpPrimitivesService)
  salt:       string             // required
  expiresAt:  Date               // required
  attempts:   number             // default 0 — per-code attempt counter (FR-024)
  consumedAt?: Date              // set when the code successfully established a session
  createdAt:  Date               // timestamps: { createdAt: true, updatedAt: false }
}
```

**Not tenant-scoped.** `markTenantScoped` is deliberately not called, for exactly the reason
`PasswordReset`'s schema comment gives: the caller is anonymous, there is no `companyId` in
`AsyncLocalStorage`, and a scoped query would match nothing and fail every sign-in as "code not
found". Reached only through `TenantContextService.runUnscoped`.

**Indexes**
- `{ userId: 1, consumedAt: 1 }` — the supersede-and-find query.
- `{ phone: 1, consumedAt: 1 }` — verification looks up by the submitted phone, not by user.
- `{ expiresAt: 1 }, { expireAfterSeconds: 0 }` — TTL self-cleanup, same as `PasswordReset`.

**The code itself is never stored, never returned, and never logged** (FR-019, FR-020). Only the
salted hash exists at rest.

**Lifecycle**

```
issued ──(correct code, unexpired, attempts < max)──▶ consumed  [terminal]
   │
   ├──(wrong code)──▶ attempts+1 ──(attempts = max)──▶ locked out  [terminal, inert]
   ├──(newer code requested)────────────────────────▶ superseded   [deleted at issue]
   └──(expiresAt passes)────────────────────────────▶ expired      [TTL-removed]
```

All four terminal states produce the **same** refusal (FR-017). The state is never reported to the
caller.

## 3. Redis key families — new (research R8, all fail closed)

None of these can live on `LoginCode`: the accumulator and the block must **outlive** the codes they
count across, and `LoginCode` is TTL-deleted at expiry.

| Key | Holds | TTL | Requirement |
|---|---|---|---|
| `login-otp:rate:{phone}` | code-request count in the window | `auth.otpRequestWindowMinutes` | FR-021, FR-022 |
| `login-otp:fails:{phone}` | failed verifications across codes | `auth.otpBlockWindowMinutes` | FR-025 |
| `login-otp:blocked:{phone}` | presence = temporarily blocked | `auth.otpBlockMinutes` | FR-025, FR-026 |
| `login-otp:pow:{seed}` | an unconsumed proof-of-work seed + difficulty | `auth.powSeedTtlSeconds` | FR-023 |

`login-otp:fails:{phone}` and `login-otp:rate:{phone}` are both deleted on a successful sign-in
(FR-029). The proof-of-work seed is deleted on first use — single-use is what stops a solved
challenge being replayed across many requests.

**Keyed by the submitted phone string, before any account lookup.** Keying on a resolved `userId`
would apply the limit only to numbers that exist, making the limit itself the enumeration oracle
FR-027 forbids — the same trap `PasswordResetService.checkRateLimit` already avoids and comments.

## 4. `JwtPayload` — one new claim

```
sid?: string    // the ActiveSession this pair was minted for.
                // Present for admin roles; ABSENT for DRIVER and CLIENT.
```

Optional in the type, but **required in effect for administrators**: an admin payload without a
`sid` is refused (research R1 — accepting it would be a permanent bypass of the session cap). A
DRIVER or CLIENT payload never carries one, and the membership check is skipped entirely for them.

Carried on **both** the access and the refresh token, for the same reason `sgen` is: a closed session
must not be renewable by its own refresh token (FR-039).

`AuthenticatedUser` **does** gain `sid?: string`, stamped from the verified payload by
`JwtStrategy.validate` and by `authenticateSocket`.

> An earlier draft of this document said the opposite — that nothing downstream of authentication
> addresses a session — and that is wrong. **`AuthController.logout` is exactly that**: it takes
> `@CurrentUser() user: AuthenticatedUser` and, under FR-035, must close *one specific session*.
> Without `sid` on that object the controller has no way to name the session it is ending, and
> FR-035 is unimplementable. The claim was inverted, not merely imprecise.

It is stamped from the **token**, never re-read from the account — the same discipline
`AuthenticatedUser.sgen` already documents for the socket path: sourcing both sides of a comparison
from the account compares a value to itself and yields a silently inert guard.

Handlers other than logout MUST NOT read it. That is a review rule, not a type-level one.

## 5. Enum additions

### `SessionRevocationCause` — one new value

```
SESSION_LIMIT_EXCEEDED = 'SESSION_LIMIT_EXCEEDED'
```

Set on the evicted session when an administrator exceeds the cap (FR-038). **Distinct from
`SIGNED_IN_ELSEWHERE` on purpose**: that cause means "your one session moved to another device",
which is a true statement for a driver and a misleading one for an administrator who still holds two
other working sessions. The message differs accordingly.

Must be mirrored in all three places that carry this vocabulary (FR-041):
`src/common/enums/session-revocation-cause.enum.ts` → `web_dashboard/src/constants/session.ts` →
the Flutter clients' equivalent. The mobile mirror gains a value it will never receive; that is
correct and is what the existing parity test enforces.

### `SessionEventType` — two new values

```
LOGIN_CODE_REQUESTED
LOGIN_CODE_VERIFY_FAILED
```

Mirroring the existing `RECOVERY_REQUESTED` / `RECOVERY_VERIFY_FAILED` pair, for FR-031. Refusals
and blocks are recorded; the code never is.

### `ErrorCode` — three new values

```
LOGIN_CODE_INVALID    = 'LOGIN_CODE_INVALID'      // the single refusal for all four failure states (FR-017)
LOGIN_RATE_LIMITED    = 'LOGIN_RATE_LIMITED'      // 429, carries retryAfterSeconds (FR-022)
CHALLENGE_REQUIRED    = 'CHALLENGE_REQUIRED'      // 400, carries the proof-of-work seed (FR-023)
```

`LOGIN_CODE_INVALID` mirrors `RESET_CODE_INVALID`'s discipline exactly: one code for wrong, expired,
superseded and locked-out alike.

## 6. `SessionEvent` — unchanged shape, one field's meaning widened

No schema change. `generation` continues to record the `sessionGeneration` in force after the event.
For an administrator event that number no longer changes between sign-ins, so rows are distinguished
by `type`, `occurredAt` and `cause` rather than by `generation`.

**Not adding `sid` to `SessionEvent`** would make "which session did this administrator hold at time
T" unanswerable — the question FR-040 asks and the reason this collection exists with no TTL. So:

```
sid?: string   // immutable. Present on admin session events; absent for DRIVER/CLIENT
               // and on account-level events (password reset, deactivation) that end all sessions.
```

## 7. Configuration — new values

All validated in `src/config/validation.ts`, surfaced through `src/config/configuration.ts`.

| Setting | Default | Purpose |
|---|---|---|
| `AUTH_MAX_ADMIN_SESSIONS` | `3` | FR-032, FR-042 — the concurrent-session cap |
| `LOGIN_OTP_EXPIRY_MINUTES` | `5` | FR-013 |
| `LOGIN_OTP_MAX_ATTEMPTS` | `5` | FR-024 — per code |
| `LOGIN_OTP_MAX_REQUESTS` | `3` | FR-021 — per phone per window |
| `LOGIN_OTP_WINDOW_MINUTES` | `15` | FR-021 |
| `LOGIN_OTP_CHALLENGE_AFTER` | `2` | FR-023 — rate-limited requests before a challenge is demanded |
| `LOGIN_OTP_FAIL_THRESHOLD` | `10` | FR-025 — failures across codes before a block |
| `LOGIN_OTP_BLOCK_MINUTES` | `60` | FR-025, FR-026 |
| `LOGIN_POW_DIFFICULTY_BITS` | `18` (`0` in test) | R7 — leading zero bits required |
| `LOGIN_POW_SEED_TTL_SECONDS` | `300` | R7 |

Defaults for expiry, attempts, requests and window deliberately match `PASSWORD_RESET_*`'s existing
values — one security posture across both anonymous code flows, not two that drift.

**Changed, not new** (research R6): `SMS_API_KEY` and `SMS_SENDER_ID` become conditionally required
when `SMS_PROVIDER=taqnyat`, using the `.allow('').default('').when(…, then: …min(1).invalid('')
.required())` idiom — `.invalid('')` included, or the requirement is silently satisfied by an empty
string.

## 8. Dashboard state — changed

`web_dashboard/src/lib/auth/token-store.ts` inverts its two storage decisions (research R9):

| Credential | Today | After |
|---|---|---|
| Access token | `localStorage` | **memory only** |
| Refresh token | memory only | **`localStorage`** if "remember me", else `sessionStorage` |

`session.store.ts`'s persisted slice is unchanged (`user`, `status`). No new store is introduced —
the sign-in flow's transient state (the phone being verified, the resend countdown, an outstanding
challenge) is component state on the sign-in screens, not global state, since nothing outside those
two screens reads it.
